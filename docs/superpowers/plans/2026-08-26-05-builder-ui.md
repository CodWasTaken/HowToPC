# HowToPC Builder UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Build the human-facing PC/homelab builder around the canonical catalog, deterministic candidate transactions, compatibility analysis, and the shared 3D digital twin.

**Architecture:** The UI is a thin client over domain actions. Zustand stores ephemeral local builder/view state; canonical build revisions and catalog data come through typed query/action boundaries. The UI never directly edits compatibility state or geometry truth. Every selection can be previewed before application, and every warning/unknown state is explainable.

**Tech Stack:** Next.js App Router, React, Tailwind CSS, shadcn/ui, Zustand, TanStack Query, React Three Fiber components from Plan 03, Playwright.

**Spec:** baseline architecture plus adversarial review.

## Global constraints

- Core builder works without login.
- Incompatible products may be inspected/previewed; default search favors compatible candidates.
- `UNKNOWN` must be visually distinct from `COMPATIBLE` and `WARNING`.
- The 3D viewport displays the resolved mechanical scene; UI code does not invent part positions.
- All agent/human mutations eventually pass through the same domain command/transaction layer.
- Mobile/narrow layouts may simplify the simultaneous panel arrangement but must preserve the build workflow.

## Exit criteria

Plan 05 is complete when an anonymous human can build a PC/homelab through the same domain transactions later exposed to WebMCP, visually inspect the real-scale digital twin, preview invalid parts without corrupting the build, understand compatibility/unknown states and calculation assumptions, and share a reproducible build.
